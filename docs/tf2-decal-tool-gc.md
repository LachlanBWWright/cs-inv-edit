# TF2 Decal Tool: legacy GC and Steam Cloud upload

## Summary

TF2 applies a Decal Tool with legacy Game Coordinator message `1023`,
`k_EMsgGCCustomizeItemTexture`. The message is not protobuf. Its packed body is
three little-endian 64-bit values: the owned Decal Tool item ID, the owned target
item ID, and a Steam UGC handle for the uploaded PNG.

The image is not carried in the GC request. Valve's historical client uploads a
PNG through Steam Remote Storage, shares that file to obtain a durable
`UGCHandle_t`, and gives that handle to the TF2 GC. A current implementation has
two possible upload routes:

1. reproduce the older UFS file upload and `FileShare` sequence; or
2. use the current unified Steam Cloud `BeginUGCUpload`/HTTP PUT/
   `CommitUGCUpload` sequence, which directly returns a UGC ID.

The second route is substantially easier to add to this repository and uses
protobuf types already generated by its Steam dependency. It still needs one
controlled live test to establish that TF2's GC accepts a UGC handle minted by
the modern endpoint.

## Legacy GC request

Valve places the economy wire structures inside `#pragma pack(push, 1)` and
defines:

```cpp
struct MsgGCCustomizeItemTexture_t
{
    uint64 m_unToolItemID;
    uint64 m_unSubjectItemID;
    uint64 m_unImageUGCHandle;
};
```

The message-specific structure is exactly 24 bytes:

| Offset | Size | Encoding | Meaning |
| ---: | ---: | --- | --- |
| `0x00` | 8 | little-endian `uint64` | owned Decal Tool item ID |
| `0x08` | 8 | little-endian `uint64` | owned target item ID |
| `0x10` | 8 | little-endian `uint64` | uploaded image's UGC handle |

It must be sent for TF2 AppID `440` as a non-protobuf GC message. Setting the
`0x80000000` protobuf mask would change the wire interpretation.

### Required legacy GC envelope

The 24-byte structure is not the complete `CMsgGCClient.payload`. Valve sends
it through `CGCMsg<T>`, and SteamKit's equivalent `ClientGCMsg<T>` serializes an
18-byte `MsgGCHdr` before the structure:

| Payload offset | Size | Encoding | Value |
| ---: | ---: | --- | --- |
| `0x00` | 2 | little-endian `uint16` | header version `1` |
| `0x02` | 8 | little-endian `uint64` | target job ID; `UINT64_MAX` for a request |
| `0x0a` | 8 | little-endian `uint64` | fresh source job ID |
| `0x12` | 24 | packed structure | `MsgGCCustomizeItemTexture_t` |

The complete outgoing payload is therefore 42 bytes. The outer
`CMsgGCClient.msgtype` remains the unflagged value `1023`; the message type is
not repeated in the legacy payload.

This repository's current `SendToGC` forwards its input as the complete
payload and does **not** add `MsgGCHdr`. Calling it with only the 24-byte
structure would be incorrect. Add an explicit legacy-GC request helper or pass
it the complete 42-byte envelope.

An encoder should write fields explicitly rather than marshal a Go struct:

```go
func encodeCustomizeItemTexture(sourceJobID, toolID, subjectID, ugcID uint64) []byte {
    payload := make([]byte, 42)
    binary.LittleEndian.PutUint16(payload[0:2], 1)
    binary.LittleEndian.PutUint64(payload[2:10], math.MaxUint64)
    binary.LittleEndian.PutUint64(payload[10:18], sourceJobID)
    binary.LittleEndian.PutUint64(payload[18:26], toolID)
    binary.LittleEndian.PutUint64(payload[26:34], subjectID)
    binary.LittleEndian.PutUint64(payload[34:42], ugcID)
    return payload
}
```

The client waits for message `1024`,
`k_EMsgGCCustomizeItemTextureResponse`, using this packed standard response:

```cpp
struct MsgGCStandardResponse_t
{
    int16  m_nResponseIndex;
    uint32 m_eResponse;
};
```

Its message-specific body is six bytes: a little-endian signed 16-bit response
index followed immediately by a little-endian 32-bit response/result value.
The incoming payload is expected to contain the same 18-byte legacy header,
making 24 bytes total. Require header version `1`, require the response target
job ID to equal the request source job ID, and then decode the body at offset
18. Do not silently accept a truncated six-byte payload unless a packet capture
from the current client proves TF2 strips the header at a different layer.

Valve's historical Decal Tool job only checks that the correlated response
arrives. A new implementation should retain the raw response value for
diagnostics and confirm success from the authoritative TF2 GC inventory update
before telling the user the tool was consumed.

## Historical `FileWrite` and `FileShare` sequence

Valve's `CApplyCustomTextureJob` performs the following operations:

1. It receives the final PNG bytes from the customization UI.
2. It computes an MD5 digest for the client's recent-image cache. This MD5 is
   cache bookkeeping, not part of message `1023`.
3. It chooses a logical Remote Storage filename such as
   `my_custom_images/1.png`.
4. It calls `ISteamRemoteStorage::FileWrite(filename, png, size)`.
5. It calls `ISteamRemoteStorage::FileShare(filename)`.
6. It waits for `RemoteStorageFileShareResult_t` and requires
   `m_eResult == k_EResultOK`.
7. It takes the returned `m_hFile` (`UGCHandle_t`) and sends it in GC message
   `1023`.
8. During cleanup it calls `FileDelete` on the logical cloud filename.

Valve comments that Remote Storage is used to get the bytes into the UGC
system. Removing the user's logical file after sharing does not invalidate the
version addressed by the UGC handle.

At the older Steam client protocol layer, the relevant UFS messages include:

| EMsg | Value | Purpose |
| --- | ---: | --- |
| `ClientUFSUploadFileRequest` | 5202 | negotiate upload of a named app file |
| `ClientUFSUploadFileResponse` | 5203 | return transfer instructions |
| `ClientUFSUploadFileChunk` | 5204 | upload through the legacy chunk path |
| `ClientUFSUploadFileFinished` | 5205 | finish/result notification |
| `ClientUFSUploadCommit` | 5251 | commit uploaded file metadata |
| `ClientUFSUploadCommitResponse` | 5252 | commit response |
| `ClientUFSShareFile` | 5232 | share an existing app file |
| `ClientUFSShareFileResponse` | 5233 | return result and `hcontent` |

Historical protobuf definitions show `CMsgClientUFSShareFile` containing
`app_id` and `file_name`; its response contains `eresult` and a fixed-width
64-bit `hcontent`. The upload negotiation includes app ID, stored and raw sizes,
SHA-1 bytes, timestamp, filename, platform flags, cell ID, and encryption
capability. Depending on the response, transfer occurs through HTTP or legacy
chunks before commit.

The current SteamKit library retains these EMsg numbers but does not expose a
high-level Remote Storage uploader. Recreating the full historical path would
therefore require implementing upload negotiation, HTTP/chunk transfer,
commit, share, response correlation, and cleanup in this repository.

## Current unified Steam Cloud upload

The current Steam protocol exposes a simpler dedicated UGC upload:

```text
Cloud.BeginUGCUpload#1
        ↓
HTTP(S) upload using the returned URL and headers
        ↓
Cloud.CommitUGCUpload#1
        ↓
42-byte TF2 legacy GC payload for message 1023
```

### 1. Begin the upload

Send `Cloud.BeginUGCUpload#1` with:

```proto
message CCloud_BeginUGCUpload_Request {
    optional uint32 appid = 1;
    optional uint32 file_size = 2;
    optional string filename = 3;
    optional string file_sha = 4;
    optional string content_type = 5;
}
```

For a decal, send:

- `appid`: `440`;
- `file_size`: exact PNG byte count;
- `filename`: `my_custom_images/<random-or-monotonic-token>.png`, using only
  ASCII letters, digits, `/`, `_`, `-`, and `.`;
- `file_sha`: the 40-character hexadecimal SHA-1 of the exact uploaded bytes
  (do not confuse this with the historical MRU cache's MD5);
- `content_type`: `image/png`.

Require unified-message `EResult == OK`, successfully decode the response, and
then require `ugcid` to be neither `0` nor `UINT64_MAX` and `url_host` and
`url_path` to be non-empty. Record `storage_system` for diagnostics, but do not
gate on a particular enum until a live response establishes the value. The
response supplies:

- a `fixed64 ugcid`;
- storage-system and timestamp metadata;
- host, path and HTTPS selection;
- all required HTTP request headers.

### 2. Transfer the bytes

Construct the URL as `https://<url_host><url_path>` and require `use_https` to
be true. Upload the exact PNG bytes with HTTP `PUT` and copy every returned
request header as a separate header value. Do not invent `Authorization`,
`Content-Type`, checksum, or storage headers beyond those returned by Steam;
setting Go's `ContentLength` is transport framing, not an extra signed header.
Treat any non-2xx response as failure and retain only a small bounded response
body for diagnostics. Disable automatic redirects because a redirected signed
PUT may leak signed headers or cease to match the signed request.

Implementation requirements include:

- a bounded HTTP client timeout;
- an exact `Content-Length`;
- no automatic content compression or transformation;
- validation that the host is a syntactically valid hostname with no userinfo,
  port, fragment, or control characters; the authenticated Steam response is
  the authority for the upload host, and deployments may additionally enforce
  observed Steam/CDN suffixes;
- a limited response-body read for diagnostics;
- cancellation through the operation context.

### 3. Commit the upload

After a begin call returns a UGC ID, call `Cloud.CommitUGCUpload#1` even when
the HTTP transfer fails, setting `transfer_succeeded` to the actual transfer
outcome:

```proto
message CCloud_CommitUGCUpload_Request {
    optional bool transfer_succeeded = 1;
    optional uint32 appid = 2;
    optional fixed64 ugcid = 3;
}
```

Require the commit call's unified `EResult == OK`, decode its response, and only
continue when `file_committed` is true. The `ugcid` returned by the begin call
is then the candidate value for `m_unImageUGCHandle` in TF2 message `1023`.

The repository's `envelop` dependency already contains generated Go types for
`CCloud_BeginUGCUpload_*` and `CCloud_CommitUGCUpload_*`. Its existing unified
message handler can send authenticated service calls and correlate replies by
Steam job ID. This avoids adding or hand-editing generated protobuf code.

### Alternative current file route

The current Cloud service also provides `ClientBeginFileUpload`,
`ClientCommitFileUpload`, `ShareFile`, and `Delete`, which more closely mirror
the old `FileWrite`/`FileShare` behavior. That path has additional cloud-file
state, block-transfer, possible encryption, platform synchronization and batch
semantics. For the Decal Tool, direct `BeginUGCUpload` is the smaller candidate
because its result already includes a UGC ID.

The vendored Steam proto currently contains the `ShareFile` request/response,
but `envelop` v0.6.1 does not expose generated Go types for them. If the direct
UGC experiment fails, update the Steam protocol dependency or its proto source
and regenerate its bindings; do not hand-write generated messages or infer
field tags. The named-file fallback must set `is_shared_file=true`, perform
every returned upload block using its declared method, offset, length, explicit
body and headers, commit the named file, call `Cloud.ShareFile#1`, reject the
invalid `UINT64_MAX` `hcontent` sentinel, and finally call `Cloud.Delete#1` only
after the GC operation has completed.

## Image validation

The historical constants are exact: `k_nCustomImageSize = 128` and
`k_nMaxCustomImageFileSize = 128*128*4 + 4*1024`, or 69,632 bytes. The download
path rejects sizes greater than or equal to that maximum. The historical client
validates downloaded custom images as PNG and expects 128 by 128 pixels. The
Official TF2 Wiki also documents 128 by 128 processing. Valve shipped an April
2024 fix for malformed custom decals that could crash clients, so new code
should be stricter than merely checking the signature.

Before any upload, validate at least:

- PNG signature and complete chunk framing;
- decoded dimensions exactly `128 × 128` unless a current controlled client
  capture establishes a different accepted size;
- byte length greater than zero and less than 69,632 bytes;
- bounded decoded memory and sane bit depth/color type;
- absence of trailing or malformed data rejected by the selected PNG decoder.

The backend should accept already-finalized PNG bytes. Reproducing TF2's UI
crop, resizing, palette/filter and template-layer processing is a separate
feature from the transport described here.

## Repository integration assessment

## Implementation status

The planned direct-UGC path is now implemented in the repository:

- `backend/internal/transport/steam_cloud_ugc.go` implements authenticated
  begin, signed HTTPS PUT, commit, and file-detail verification.
- `backend/internal/transport/tf2_legacy_gc.go` implements PNG validation, the
  42-byte legacy request, correlated 24-byte response decoding, and inventory
  reconciliation.
- `tf2.customization.decal-apply` exposes the operation through the existing
  generic operation API, guarded by `enableTf2Customization` and permanent
  action confirmation. It accepts `toolItemId`, `subjectItemId`, and
  `pngBase64`.
- `TF2DecalTool.tsx` adds the eligible-item UI, owned-tool selection, PNG file
  selection, and explicit permanent-action confirmation.
- Focused transport tests cover PNG validation, legacy byte layouts, inventory
  confirmation, signed PUT behavior, endpoint validation, and HTTP failures.

The named-file `FileWrite`/`ShareFile` fallback is documented but not
implemented because the direct UGC route supplies the required handle with
less protocol surface. A controlled live test is still required before this
path should be considered runtime-verified against the current TF2 GC.

The repository already has:

- an authenticated Steam CM connection;
- authenticated unified-service calls with job correlation;
- TF2 AppID `440` presence and GC hello/welcome handling;
- TF2 protobuf inventory decoding;
- raw non-protobuf `SendToGC` support.

The remaining verification and hardening pieces are:

1. a fake-CM integration harness for begin/commit/GetFileDetails unified calls;
2. one controlled upload-only compatibility test;
3. one explicitly authorized end-to-end item application;
4. identification of the exact current TF2 custom-texture attribute for a
   stronger post-operation reconciliation assertion.

Keep the transport work isolated from the application/API work:

### Exact Cloud call data

For `Cloud.BeginUGCUpload#1`, construct:

```go
&steampb.CCloud_BeginUGCUpload_Request{
    Appid:       proto.Uint32(440),
    FileSize:    proto.Uint32(uint32(len(pngBytes))),
    Filename:    proto.String(filename),
    FileSha:     proto.String(hex.EncodeToString(sha1Sum[:])),
    ContentType: proto.String("image/png"),
}
```

The operation must reject a file that cannot fit in `uint32` before conversion,
although the stricter 69,632-byte decal limit makes that impossible after PNG
validation. Route the authenticated unified call for AppID `440` using method
name exactly `Cloud.BeginUGCUpload#1`.

For `Cloud.CommitUGCUpload#1`, construct:

```go
&steampb.CCloud_CommitUGCUpload_Request{
    TransferSucceeded: proto.Bool(httpUploadSucceeded),
    Appid:             proto.Uint32(440),
    Ugcid:             proto.Uint64(beginResponse.GetUgcid()),
}
```

For optional verification, call `Cloud.GetFileDetails#1` with AppID `440` and
the UGC ID. Require returned `details.appid == 440`, matching UGC ID, matching
file size, matching filename, matching SHA-1 when populated, and
`steamid_creator == s.activeSteamID` when populated. A missing optional field
is not a mismatch; a populated conflicting field is.

### Exact HTTP behavior

The upload function should:

1. reject `use_https == false`, empty host/path, a host containing a port,
   userinfo/control characters, or a path that does not begin with `/`;
2. parse `"https://" + host + returnedPath` with `net/url`, validate the parsed
   scheme/host and require `EscapedPath()` plus `RawQuery` to reproduce the
   returned path and query byte-for-byte; normalization can invalidate a
   signature, so reject rather than rewrite a non-round-tripping value;
3. create a context-bound `PUT` whose body is a fresh reader over the exact PNG
   bytes and whose `ContentLength` equals their length;
4. add every returned header with `Header.Add`, rejecting header names/values
   containing CR or LF;
5. use an HTTP client with redirects disabled and bounded connect, TLS-header,
   response-header and whole-operation timeouts;
6. accept only status `200..299`, close the body on every response, and read at
   most a small fixed diagnostic limit on failure;
7. call commit with `transfer_succeeded=false` after any attempted PUT failure,
   while returning the original PUT error augmented if the failure commit also
   fails.

Never log the full URL, query string, or returned request-header values because
they may contain upload authorization material.

### Tests required before a live request

Add table/golden tests for:

- the exact 42-byte request, including offsets and little-endian values;
- rejection of response payloads shorter or longer than 24 bytes, wrong header
  version, wrong target job ID, zero source job ID, and the successful decode;
- PNG dimensions, zero/truncated/corrupt input, and the `< 69,632` byte limit;
- begin/commit unified `EResult` failures, protobuf decode failures, invalid
  UGC sentinel values, and `file_committed=false`;
- signed headers with repeated names, redirect refusal, non-2xx responses,
  cancellation, timeout, exact body bytes, and the failure-commit path;
- `GetFileDetails` identity/size/SHA mismatches;
- concurrent operation serialization and unrelated GC message filtering;
- no GC message sent when validation, upload, commit, or verification fails;
- one successful fake end-to-end sequence asserting method names, AppID,
  request fields, HTTP transfer, commit, 42-byte GC payload, correlated response
  and inventory confirmation.

The live test should use an account and disposable eligible items supplied for
that purpose. It should first upload a harmless 128 by 128 PNG, optionally
verify it through `Cloud.GetFileDetails`, then apply it to an eligible target.
The test must stop before consuming the Decal Tool if upload or UGC verification
does not match expectations.

## Recommended implementation order

1. Add pure PNG validation and the 42-byte request/24-byte response codecs,
   with golden byte tests.
2. Add a narrow `uploadTF2DecalUGC` implementation using
   `Cloud.BeginUGCUpload#1`, signed HTTP PUT, and
   `Cloud.CommitUGCUpload#1`.
3. Verify the resulting handle with `Cloud.GetFileDetails#1`, checking AppID,
   UGC ID, creator, filename, size and SHA-1 when returned.
4. Add the TF2 GC operation and wait for both message `1024` and the inventory
   update.
5. Exercise upload-only behavior against Steam. Do not consume an item yet.
6. After inspecting the uploaded object, perform one explicitly authorized
   end-to-end application.

## Uncertainties requiring live verification

The legacy GC layout and Valve's historical `FileWrite`/`FileShare` behavior
are directly sourced and high confidence. These current-runtime details remain
to be verified:

- whether TF2 GC accepts a handle returned directly by
  `Cloud.BeginUGCUpload#1`, rather than one produced by named-file `ShareFile`;
- whether the current game/GC imposes validation beyond the historical exact
  `< 69,632`-byte and `128 × 128` rules after the 2024 hardening;
- whether the current GC response populates `m_eResponse` meaningfully;
- how quickly the authoritative TF2 SO inventory update follows response
  `1024`.

If the direct UGC handle is rejected, the fallback is the current named-file
flow (`ClientBeginFileUpload`/HTTP blocks/`ClientCommitFileUpload` followed by
`ShareFile`), not an inferred binary payload.
